# Privacy and data flow

Slipstream has no accounts, advertising, analytics, or telemetry.

## Data that stays on the Mac

- Screenshots and Apple Vision OCR processing.
- App settings and bounded saved-term records.
- API keys, encrypted through macOS `safeStorage`.
- Text processed by Ollama when a local model is selected.
- Private staged settings copies and confirmed startup-recovery archives.

Temporary screenshot files are deleted after OCR. Full source text is not saved to history by the supported V1 flow.

Apple Vision OCR runs in a capability-minimized subprocess. It receives only `PATH`, `SLIPSTREAM_OCR_CACHE`, `HOME`, `CFFIXED_USER_HOME`, `TMPDIR`, `TMP`, and `TEMP`; its cache, HOME, and temporary directories are created locally with mode `0700`. API keys and other parent-process environment values are not inherited. Release tests generate and process their fixed fictional OCR image locally and do not send it to a network service. The production OCR cache may persist inside Slipstream's private application data so the app can reuse its compiled helper; it is not represented as per-run temporary data.

During cold start or a renderer reload, the main process may hold at most one normalized capture event until the matching renderer has installed its clipboard and screenshot listeners. The slot is memory-only and latest-wins; clipboard text is capped at the ordinary 10,000-character source limit, is never logged or persisted by this handoff, and is cleared when renderer ownership changes, the window closes, or the app exits. A trusted main-frame readiness handshake releases it once. Passive clipboard monitoring uses the same bounded slot but does not reveal or focus the window.

At startup, Slipstream may create a private mode-`0600` sibling copy of the existing settings file so it can validate and migrate without touching the original. If parsing, schema validation, migration, or storage access fails, the original remains in place and normal persistent runtime stays blocked. The user can retry or explicitly confirm a start-fresh recovery. That recovery renames the complete old settings file to a local mode-`0600` recovery archive, then creates new settings; if fresh creation fails, Slipstream restores the original. The archive is not uploaded or re-imported automatically.

Because the recovery archive is the complete prior settings file, it may contain all data that file previously held, including saved terms, settings, bounded excerpts, and encrypted credential material. Slipstream displays only its filename during recovery. A later full data reset removes recognized recovery archives as well as the active store.

Saved API keys are represented in the renderer only by provider-specific `has key` flags. The encrypted value is not returned to the Settings window and cannot be revealed there. Settings shows a reveal action only for a replacement value the user is currently entering; clearing, saving, deleting, or changing providers returns that field to a concealed state.

If a replacement credential, endpoint, or model write fails and the user explicitly discards that editor, Slipstream removes the matching operation from its in-memory generic retry queue, together with any paired full-analysis pause. Retrying unrelated failed settings cannot later persist the abandoned credential or destination.

For a custom provider, the URL origin is the credential trust boundary. Changing only the path on the same origin retains the encrypted key. Changing the scheme, host, or port commits the new URL and an empty custom-provider key in one atomic settings write; if that write fails, the complete old URL/key boundary remains in place. The renderer clears its saved-key indicator only after the matching main-process response confirms that transition, so an old key cannot be retried or sent to the new origin.

Endpoint location is a separate fail-closed privacy boundary. Slipstream calls a custom service “on this Mac” only for a validated HTTP loopback address (`localhost`, any canonical `127/8` address, or `::1`). A validated public HTTPS custom endpoint is online. HTTPS loopback, public HTTP, credentials embedded in a URL, unsupported ports/paths, and invalid or missing values are not given a reassuring location label and cannot start formal analysis. Ollama is restricted to validated HTTP loopback as well; unsafe legacy values are cleared, runtime snapshots suppress manually injected values, and an unknown Ollama destination is never shown as this Mac in the task surface or menu bar. Immediately before source submission, the main process revalidates the saved destination and uses the same settings snapshot for location metadata and the actual request. Custom and Ollama analysis reject all redirects before a second request; public custom HTTPS additionally uses a safety-checked, request-pinned DNS result. Custom non-2xx bodies are cancelled without parsing so an echoed source or credential cannot enter an error or log. Successful custom responses request identity encoding and are rejected before parsing when declared or streamed content exceeds 4 MiB. Slipstream connecting only to loopback does not prove the compatible service itself stays offline: that service may network, forward, retain, or charge according to its own configuration.

Each saved-term record contains only the term, its bounded explanation, a strict classification enum, a strict provenance enum, and the shortest relevant source excerpt. Legacy or invalid metadata fails closed to `other / unknown`; it is never upgraded to inferred or official trust. Version 2 backups contain only the term, explanation, classification, and the provenance label at export time. They exclude the retained excerpt, local IDs, timestamps, settings, and credentials. Because the evidence needed to re-establish `original`, `inference`, or `official` provenance is absent, those v2 labels import as `unknown`; the preview counts these downgrades, and lower-trust imported data cannot overwrite a stronger local record. Version 1 backups remain importable but are labeled `other / unknown` after import.

When the user clears a draft or result, Slipstream may keep one recovery snapshot in memory for up to ten seconds. The interface shows the remaining undo time, never writes that snapshot to history, and drops any previous official-verification approval before restoration. If the result has an edited guided reply, the same memory-only snapshot preserves its text, chosen real-world status, progress exception, and selection so Undo restores the user's work exactly.

While the same Slipstream window session remains open, the renderer also keeps one bounded temporary interruption-recovery snapshot in browser-managed session storage. It may contain the current source, correction draft, completed action brief, result text, bounded OCR/source metadata, the result's bounded `local`, `local-loopback`, `online`, or `unknown` processing-location enum, its provider enum, and an unsent guided-reply draft with its selected status and cursor selection. The reply is bound to a short non-reversible model-identity hash; the full reply model is not duplicated. The snapshot expires 30 minutes after its last active refresh and is removed when the user restores, discards, or explicitly clears it, or when the window session ends. It does not become Slipstream history, does not sync, and does not survive an application restart. Slipstream excludes settings drafts, API keys, service addresses, custom analysis prompts, clipboard consequence IDs and write receipts, clipboard request IDs, reply-content/version identities, task-generation markers, and official-verification approval IDs from this snapshot. Invalid provider/location values fail closed, and unknown fields hidden inside analysis provenance are removed so an endpoint or credential cannot be smuggled into recovery metadata.

If processing a replacement source fails while an older valid result exists, the failed source is held separately only in renderer memory so retry cannot accidentally submit the older visible source. Opening it for review keeps the same memory-only ownership while providing the correction controls, so returning to the older result can still reopen or retry it. Interruption recovery stores only the older valid result—not the failed source, its correction, or the related retry notice. A successful retry, explicit task clear, full data reset, or renderer interruption removes the special slot.

After a renderer crash or reload, the user chooses whether to restore or discard the temporary snapshot. Interrupted analysis, provider validation, screenshot capture, and official verification are stopped and never restart automatically. A restored result cannot reuse prior official-lookup approval; if lookup is still needed, the user must reanalyze and approve again. A restored reply keeps its text and selected status but clears any prior “the checklist is stale” exception, so that real-world progress must be confirmed again before copying. It is restored as not copied because no clipboard receipt or copied-state claim is recovered; the user must check and copy it again. This recovery is best-effort: a full app exit, operating-system termination, expired or corrupted storage, or a failure before the latest snapshot was written can leave nothing recoverable.

A successful app-owned clipboard write also creates one sender-bound, main-process consequence marker containing only an opaque random ID. If the renderer is interrupted, Slipstream keeps this marker so the replacement interface does not silently imply the system clipboard is safe. Recovery does not read, clear, or overwrite the clipboard and receives no copied text, fingerprint, receipt, copy kind, or task identity. It receives only the opaque ID and warns that the earlier content may remain. The warning survives repeated renderer reloads. Its exact ID is removed only when the user confirms that they checked or manually overwrote the clipboard, a later successful app-owned write replaces the consequence, a confirmed full reset follows the preserve acknowledgement, the owning window is destroyed, or the application finally exits. The ID is not stored in browser session recovery, settings, history, logs, or release artifacts.

Copying a result, action checklist, reply, official-source URL, saved-term scope, support summary, or recovery command places that chosen content in the macOS system clipboard, where other applications may be able to read it. Generated replies cannot be copied while recognized template placeholders remain. A reply copy becomes visibly pending before the clipboard write begins and is settled against its originating request, task, and non-plaintext content identity. An unchanged reply becomes copied; an edit or status change before settlement becomes outdated; and a write that finishes after the task was cleared is retained without implying the closed task still owns the current draft. Clearing and undoing the task never triggers a second write: an exact restored reply may reconcile to copied, while an edited restoration remains outdated. A late completion cannot mark another task or newer draft as copied.

Every app-provided copy uses one App-owned write transaction. Ownership is acquired synchronously before native IPC, competing copies are blocked until settlement, and application quit or full-data reset waits for the outcome. Settlement is request-bound: a failed replacement restores a still-live prior consequence, while an expired prior consequence or stale settlement cannot become current again. Expired, failed, malformed, or mismatched outcomes keep the application open, and resolving the clipboard item never bypasses unrelated draft, result, task, or Settings warnings. This coordination stores metadata only. The renderer retains only notice, request, operation, opaque consequence, and reply-version metadata; the main process retains only the sender-bound opaque consequence. Neither layer keeps another plaintext copy for cleanup. Dismissing a clipboard notice hides presentation without discarding unresolved settlement or consequence state; TTL expiry removes that state.

Slipstream offers no post-copy automatic clear action and the production preload exposes no clipboard-clear channel. One authoritative consequence notice follows the user across the task, Settings, Saved Terms library, and first-use surfaces. Leaving a task relabels only task-scoped copies as retained; independent Settings or Saved Terms consequences remain unchanged. If the user tries to quit while a consequence is live, Slipstream snapshots that risk before the quit interface is presented and requires an explicit choice to continue using the app or knowingly exit while preserving the system clipboard. The user may inspect or manually overwrite the clipboard; Slipstream acknowledges only the exact current consequence and never claims that clipboard content was removed. Preserve-only is not erasure: sensitive copied text can remain readable to other applications or clipboard-history tools until the user overwrites it, and Slipstream deliberately does not read back the clipboard to verify that manual overwrite. Opening an official-source URL hands only that validated public HTTPS URL to the system default browser; opening the page does not submit the captured source and does not promote a retrieval receipt to verified evidence.

Global-shortcut readiness contains only the configured accelerator text and whether macOS registered it. The shortcut recorder derives one canonical accelerator from the key combination being pressed and does not retain a keystroke history. Slipstream keeps the resulting status in application memory, shows it in Settings, and includes the same accelerator/boolean state in the preview-before-copy support summary. It does not contain clipboard text, screenshots, submitted source text, or credentials, and it is never sent automatically.

## Data that can leave the Mac

Before submission, the capture panel shows the current processing destination beside the generate action at every supported window size. It states whether the full source stays on this Mac or is sent to the named online provider, separates model analysis from optional official-source lookup, and links directly to changing the processing method.

After submission, the processing surface keeps the destination and transfer consequence visible but does not repeat any raw source excerpt. It exposes only a source-type label and the exact retained character count, with an explicit explanation that content is hidden to reduce shoulder-surfing exposure. The complete source remains in the current renderer task state so a confirmed cancellation can restore it; the metadata summary never replaces or truncates that recovery copy. The expanded completion details retain the destination that produced the result, even if Settings later changes. Tray/support summaries and quit/cancel prompts use the same bounded location vocabulary and never include the endpoint host, port, path, URL, API key, or source text.

Clipboard monitoring is off by default and requires an explicit, destination-specific confirmation before it can be enabled. Once enabled, a new non-empty clipboard text is read automatically without another click or shortcut only when the task surface is empty. With Ollama, that text is analyzed on this Mac and is not sent to a model provider. With a cloud model, the complete text is sent to the named provider and may be recorded or charged under that provider's policy. With free translation, it is sent to Google Translate and may fall back to MyMemory; those free endpoints may record requests, rate-limit, or be unavailable. Users should turn monitoring off before copying passwords, one-time codes, identifiers, or other text they do not intend Slipstream to process. Slipstream does not create source history from monitoring. If a task, draft, verification, or result is already present, later copies are not sent automatically and do not replace that content; only the latest waiting copy is retained in renderer memory until the user processes, ignores, disables monitoring, or exits. The macOS menu receives only a waiting flag and count, never the waiting text. While monitoring is active, the main task surface and macOS menu keep the destination and an off action visible, including when the window is hidden. Closing monitoring prevents future clipboard triggers, discards the waiting copy without sending it, and does not cancel an analysis already in progress. A failed write preserves and explains the last confirmed on/off state.

Option+C uses the same memory-only waiting slot whenever a task, verification, draft, recovery prompt, result, or the Settings screen owns the visible state. An explicit shortcut capture takes priority over later automatic monitor events until the user processes or ignores it. In an otherwise empty task surface, its short automatic handoff remains valid only while the same capture and source revision still own the visible draft. Any edit cancels that handoff before provider submission—even if the user undoes back to identical text—keeps the latest draft as manual input, and requires Generate or Command+Enter. Unsaved source correction, an unsent draft, and the ten-second clear undo window keep their current content intact while the waiting card names the exact state that processing would abandon. Choosing the safe action removes the waiting text and returns focus to the current editor, undo control, monitoring status, or result heading. Recovery, the saved-term library, settings confirmation, and app quit confirmation remain modal and cannot be bypassed by processing the waiting text. The default screenshot shortcut, Option+Shift+S, stores only a pending screenshot intent—no image, selection, or source text—and asks whether to stop active work or continue it. Existing custom bare function keys such as F2 are preserved; because most Apple keyboards require Fn/Globe for them, Slipstream labels that limitation and offers the recommended combination instead of claiming registration proves the physical key will fire. Screenshot capture follows the same foreground ownership boundary and cannot start selection behind another decision. Before a stop request is sent, the user may still cancel the screenshot and continue the task. Once stopping begins, that request cannot be withdrawn: the continue action disappears, the pending state says so directly, and an unconfirmed stop remains retryable without claiming the task has resumed. After the foreground state is resolved, either request remains a focused start-or-keep choice and never auto-starts. While Settings is open, neither shortcut starts hidden analysis: unsaved connection fields require an explicit discard decision, provider validation must receive a confirmed stop, and guided setup keeps the request pending until a processing mode is enabled. Choosing to continue settings leaves the request visible for later action; an empty clipboard produces only an in-settings error. Screenshot selection starts only after the underlying cancellation task settles or work completes. A bounded stop timeout is reported as still running and remains retryable; it is never presented as successful cancellation. The main process rejects screenshot requests during provider validation, analysis, or official verification and never treats capture as implicit permission to abort another request.

- A cloud model receives the text the user explicitly submits when that provider is selected.
- A custom HTTP loopback service receives the text the user explicitly submits through this Mac's loopback interface. Slipstream does not follow redirects, but the compatible service can independently forward or retain the text; review that service's configuration before treating the workflow as offline.
- Full analysis first sends the submitted source to the configured model. If that response proposes tasks, materials, or deadlines, Slipstream may send the same source and a bounded summary of those claims to the same configured model once more for a short independent review. The review is limited to deciding which claims describe explicit, unfinished user work; it does not use a new destination or send credentials inside the prompt. A cloud provider may record or charge for both requests.
- Before a cloud model can be enabled for full analysis, the user-triggered readiness check sends a fixed fictional compatibility message with built-in `action-brief.prompt.v4`. If that response proposes task claims, the same fictional source and bounded claims receive the same short review. Slipstream then runs the result through the parser and `ActionBriefV1` validator and applies additional probe-specific checks for grounded translation, deadline, material, actions, terms, and process context. The candidate and structured schema remain v1-compatible, and valid JSON alone does not pass. It does not send screenshots, clipboard content, task text, saved terms, or the optional custom analysis preference. This is a representative compatibility probe, not a guarantee for arbitrary inputs; the provider may still record or charge for both requests under its own policy.
- Replacing a credential after a runtime failure requires another user-triggered readiness check before full analysis is re-enabled. The current task remains in renderer memory while Settings is open; the compatibility request still uses only the fixed fictional message and never reuses the failed task text.
- The free translation backend sends submitted text to Google Translate first and sends the complete text again to MyMemory only if Google does not return a usable translation. The submit and in-progress surfaces disclose this sequence. It is therefore not a local mode.
- If neither translation endpoint returns a usable result, Slipstream keeps the submitted source and previous valid result in the current renderer session. Recovery does not send credentials or run a fictional account check for those unauthenticated endpoints; the user explicitly retries or chooses a different local/online processing path before another transfer.
- Opening full-analysis setup from a translation-only result does not submit the retained task to the selected model. The source and translation stay in the current renderer session while configuration is incomplete; transfer occurs only after the provider passes validation, the user enables full analysis, and the user explicitly reruns the task.
- Switching from a configured online model to free translation requires an explicit choice about the saved provider credential. Keeping it leaves the encrypted credential on this Mac and never sends it to Google or MyMemory. Deleting it requires a second confirmation, clears the provider connection locally, and does not clear the current source or previous result. The mode remains paused if the settings transaction cannot finish, so a partial write cannot silently resume processing under an ambiguous destination.
- Official verification sends only a bounded query and/or candidate official URL. The verification API rejects fields that resemble full email or source text.

Default official verification policy is **Ask first**. `Local only` performs no verification request. `Official auto` discovers or retrieves only eligible official sources automatically. The built-in GOV.UK discovery adapter sends only a minimized query to GOV.UK's public Search API; it never sends the captured source text.

Slipstream cannot control a third-party provider's retention policy. Review the chosen provider's policy before submitting sensitive school, immigration, employment, financial, legal, or medical content.

## Local deletion

Settings provide controls to remove saved terms, any legacy history, credentials, or all in-app local user data. A full reset cannot begin while an app-owned clipboard write is still settling. After settlement, the user explicitly chooses to preserve the system clipboard and the main process issues a cryptographically random, sender-bound, one-time reset ticket for the exact current consequence. Only then does the renderer clear the current source, result, self-reported action progress, guided-reply work, ten-second undo snapshot, pending clipboard/screenshot capture, and same-window interruption-recovery record. Commit consumes the same ticket, revalidates the consequence, and clears saved terms, encrypted credentials, settings, monitoring state, shortcut registrations, in-flight request authority, and recognized startup-recovery archives. Slipstream returns to the first-use choice only when both stages confirm. If the persistent stage cannot be confirmed, the interface explicitly says the current session has already been cleared and keeps only the remaining deletion retryable.

The macOS system clipboard is not part of Slipstream's application data store and is never included in “clear application data.” Reset always preserves it. A missing preserve choice, expired ticket, mismatch, replay, cross-sender use, renderer loss, or changed consequence blocks persistent deletion. The user must inspect or overwrite older clipboard content through macOS or another deliberate copy action; Slipstream never reads, clears, or overwrites it automatically during reset.

Individual API-key deletion and delete-while-switching both require a separate confirmation; Escape or the safe action keeps the credential. The supported V1 flow does not retain new source history. Deleting the app alone may not delete its Electron settings directory or recovery archives; use full data reset first when the app remains operable.
